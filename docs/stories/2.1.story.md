### Data Models
From [Source: architecture/data-models.md] and existing database schema:
- **Existing Project Model**: Projects table exists with id (bigint), name, status, company_id, uuid, timestamps
- **New Task Model Requirements**: 
  - project_id (bigint) - FK to projects(id)
  - assignee (bigint) - FK to users or parties for task assignment
  - title (string) - Task name/title
  - description (text) - Detailed task description
  - status (string) - Task workflow state (To Do, In Progress, Done)
  - priority (string) - Task priority level
  - due_date (date) - Task deadline

### Database Schema Design
From [Source: architecture/database-schema.md]:
- **Pattern**: Follow PostgreSQL schema design patterns used in existing tables
- **Naming**: Use snake_case column names, table name should be "tasks"
- **Indexes**: Add indexes on foreign keys and frequently queried columns
- **Constraints**: Add proper FK constraints and check constraints where applicable
- **UUID**: Include UUID column with default uuid_generate_v4() like other tables

### API Specifications
From [Source: architecture/rest-api-spec.md]:
- **DTO Pattern**: Follow existing pattern with struct embedding Body field
- **Response Format**: Use standard response wrapper (ResponseData, ResponseMessage)
- **Validation**: Required fields use `required` tags, optional use `nullable: true`
- **Field Types**: Match OpenAPI 3.0 specification types (integer/int64, string, boolean)

### File Locations
From [Source: architecture/source-tree.md]:
- **Generated Models**: Will be created in `gen/db/model/tasks.gen.go` (auto-generated)
- **Generated Queries**: Will be created in `gen/db/query/tasks.gen.go` (auto-generated)
- **DTOs**: Create in `api/dto/task_dto.go` following existing patterns

### Technical Constraints
From [Source: architecture/tech-stack.md] and [Source: architecture/coding-standards.md]:
- **Database**: PostgreSQL 14+ with GORM v1.25+ for ORM
- **Code Generation**: Use GORM Gen for type-safe queries
- **Critical Rule**: Never manually edit files in `gen/db/` - always regenerate with `make models`
- **Repository Pattern**: All database access must use repository pattern with generated models

### Integration Points
From existing codebase analysis:
- **Parties Table**: FK relationship to existing parties(id)
- **Projects Table**: FK relationship to existing projects(id)
- **Users/Parties**: Assignee field should reference existing user management system
- **Company Isolation**: Tasks should be company-scoped through project relationship
- **Event System**: Consider domain events for task creation (future stories)

### Testing
From [Source: architecture/test-strategy-and-standards.md]:
- **Unit Tests**: Create `*_test.go` files alongside source code using Go native testing + Testify v1.8+
- **Test Coverage**: Minimum 80% line coverage for unit tests
- **Integration Tests**: Use Testcontainers PostgreSQL for database testing
- **Test Location**: Tests in same directory as source files with `*_test.go` naming
- **Mocking**: Use Testify/mock and GoMock for interface mocking
